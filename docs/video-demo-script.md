# DBAgent 两分钟视频演示：Snake Arena

本视频使用两次真实、连续的编程任务来演示 DBAgent：第一轮在空工作区从零建立一个可运行的全栈网页贪吃蛇；第二轮在同一个项目上增加“疯狂模式”。这样既能展示新项目交付能力，也能展示 Agent 对已有 repository 的理解、跨前后端修改和自验证能力。

可以把等待、重复读取与依赖安装加速，但不能伪造工具调用、测试、构建结果或最终状态。成片为 MP4，时长不超过 120 秒、文件不超过 200MB；不要录入 config.toml、api_key.txt、环境变量、provider URL、token 或个人路径。

## 这个项目最终做什么

Snake Arena 是一个浏览器中的贪吃蛇游戏。

    React 前端：昵称输入、方向键控制、画布/页面游戏界面、分数、重新开始、排行榜切换。
    FastAPI 后端：提供健康检查、提交成绩和读取排行榜的 HTTP API。
    SQLite：持久保存昵称、分数、模式和时间，重启后排行榜仍存在。
    经典模式：随机食物、成长、计分、撞墙/撞自己后结束。
    疯狂模式：障碍物、每五个普通食物生成的限时金色食物、随分数加速、减速道具、独立排行榜。

第一轮要建立前后端和数据库的最小完整闭环；第二轮不能重新创建项目，而要阅读并复用第一轮已有实现。这一点比只让模型写一个单文件游戏更能体现 Coding Agent 的 repository-aware 能力。

## 录制前准备

1. 创建一个真正空的演示目录，例如 C:\demo\snake-arena。
2. 在该目录初始化 Git 并暂存空基线；不要创建 commit。

    cd C:\demo\snake-arena
    git init
    git add .

3. 在这个目录启动 DBA --ui web。浏览器工作区必须显示 snake-arena，而不是 DBAgent 源码目录。
4. 录制前先完成一次不录屏的真实 run，确认模型、网络、Node、Python 和依赖安装能用。浏览器 UI 的步数建议设为 80；如果中途需要更多预算，展示用户调整步数或用继续执行在同一会话完成。
5. 第一轮成功后保留 workspace 和 session，直接输入第二轮 prompt。不要手工提前修改任何游戏文件。

## 第一轮：从零创建 Snake Arena

在空 workspace 输入以下完整 prompt：

> 从零创建一个全栈网页版贪吃蛇项目 Snake Arena。
>
> 前端使用 React，后端使用 FastAPI，数据库使用 SQLite。
>
> 游戏需要支持经典贪吃蛇玩法：方向键控制、随机食物、吃到食物后增长并增加分数、撞墙或撞到自己后游戏结束、支持重新开始。
>
> 玩家开始前可以输入昵称。
>
> 游戏结束后，前端需要调用后端接口提交玩家昵称和成绩。
>
> 页面右侧显示历史 Top 10 排行榜，数据从后端获取。
>
> 请完成完整项目结构、前后端代码、数据库初始化和接口联调，并自行运行检查项目是否能够正常工作。

这一轮应该观察到的工程动作：

1. 计划面板明确列出环境/结构、React 经典玩法、FastAPI/SQLite、前后端联调、验证和交付。
2. Agent 先检查空目录和 Python/Node 可用性，再建立前端和后端各自的 manifest、源码、测试或 smoke check、README。
3. Agent 通过本地工具创建文件，运行后端测试或 API 检查、前端 build/测试/启动检查，并让验证状态反映真实结果。
4. 完成后在变更面板看到新增文件与行数，在最终卡片看到启动命令、检查命令和 VERIFIED 或诚实的限制。

第一轮不应只生成一个 HTML 文件，也不应因为“workspace 为空”而停下。若本机缺少 npm、Python 包或网络，Agent 应保留证据、说明缺少什么，而不是假装已完成全栈联调。

## 第二轮：在现有项目增加疯狂模式

等待第一轮结束后，在同一个 browser session 与同一个 workspace 输入以下 prompt：

> 现在在现有 Snake Arena 项目的基础上增加“疯狂模式”，不要重新创建项目。
>
> 开始游戏前允许玩家选择经典模式或疯狂模式。
>
> 疯狂模式增加以下机制：
>
> 1. 地图随机生成障碍物，撞到障碍物游戏结束。
> 2. 每吃 5 个普通食物，生成一个限时 5 秒的金色食物，吃到获得额外分数。
> 3. 随分数增加逐渐提升蛇的移动速度。
> 4. 增加一种随机出现的减速道具，吃到后短时间降低移动速度。
> 5. 排行榜需要区分经典模式和疯狂模式，玩家可以切换查看两个排行榜。
>
> 请先阅读和理解现有项目，再决定需要修改哪些前端、后端和数据库代码。尽量复用现有实现，不要破坏经典模式。
>
> 修改完成后自行运行和检查，如果出现前后端接口、数据库或游戏逻辑问题，请继续修复。

这一轮应重点展示：

- 计划被新的“疯狂模式”目标覆盖，而不是错误显示第一轮的初始化计划；
- repo map、file tree 或代码预览显示 Agent 正在读取已有前端、后端、数据库和测试；
- 修改同时涉及游戏状态/规则、模式字段或数据库迁移、API 和排行榜 UI；
- 经典模式仍被保留，新增模式不会破坏已有提交成绩流程；
- 如果检查失败，失败结果进入 observation，Agent 根据它继续修复；修改后的旧验证证据会变 stale，必须重新验证。

## 剪辑与现场说明

保留以下镜头：两次 prompt、两个计划、第一轮文件结构/验证、第二轮阅读已有代码、跨层变更、至少一次真实检查结果、最终 VERIFIED 或诚实的 INCOMPLETE。

不要念“正在读取文件”。使用因果说明：

    “空目录段证明它能建立完整交付物；疯狂模式段证明它能理解已有架构并复用而非重写。”
    “前端规则、后端 API、SQLite 模式字段和排行榜是不同层，所以计划与 patch 都要跨文件。”
    “模型不能自证完成。每次修改都会让旧验证失效，最后必须重新跑当前代码上的检查。”
    “如果本机依赖确实不可用，Agent 会输出证据和 INCOMPLETE；这比虚假成功更符合工程实践。”

- [ ] workspace 从头到尾是同一个 Snake Arena 演示目录。

- [ ] 计划、变更、验证、最终结果相互一致。
- [ ] 视频展示的是实际运行，可以加速但没有伪造。
