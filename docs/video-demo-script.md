# DBAgent 两分钟演示视频脚本

本脚本按题目要求设计：视频展示一次真实编程任务的完整闭环，再用极短说明解释
实现。成片使用 MP4、时长不超过 2 分钟、体积不超过 200MB。请只录制干净的演示
workspace；不要展示 `config.toml`、`api_key.txt`、环境变量、浏览器访问 token 或任何
真实 provider URL。

## 为什么选这个任务

使用仓库内的 `tests/fixtures/taskboard_repo` 副本，演示下面这条任务：

> `TaskService.search` 的文档要求按任务标题或标签搜索，但当前实现忽略标签。请定位
> 问题，先添加只按标签命中的回归测试，再做最小修复；分别运行针对性 pytest 和完整
> pytest，通过后用 git diff 总结。

这是一个真实的多文件 Python 项目：有 model、repository、service、CLI 和自动化测试。
任务可自然展示“读代码 → 发现缺口 → 测试失败 → 原子 patch → 定向测试 → 全量测试 →
验证”的链路；它比从空目录生成大型游戏更适合两分钟内稳定、可解释地证明 agent 的工程
能力。演示时不需要把每次读取文件都展示给观众。

## 录制前准备（不录入视频）

1. 从一个干净演示目录复制 `tests/fixtures/taskboard_repo`，不要直接修改 fixture。
2. 在演示副本内初始化 Git，并将初始文件暂存为基线；不要让 DBAgent 自动提交：

   ```powershell
   git init
   git add .
   ```

3. 在 DBAgent checkout 中完成一次安装：`./scripts/install-dba.ps1 -Install`。
4. 在不录屏的环境中确认本机凭据文件有效；录制时只在任务目录运行 `DBA --ui web`。
5. 确认浏览器工作台的 workspace 是演示副本。录制窗口只保留浏览器、必要时再保留一
   个显示 pytest 的终端；关闭含私密信息的终端和编辑器标签。
6. 先完整跑一遍，确认本次 provider 与网络正常。录制时允许将中间等待和重复阅读以
   3–5 倍加速，但不能伪造测试输出或验证结果。

## 推荐镜头与逐段讲稿

| 时间 | 画面 | 可以直接说的话 |
| --- | --- | --- |
| 0–10 秒 | DBAgent browser workspace、仓库树与空闲会话 | “这是 DBAgent，DB 指 Database，强调它把任务状态、仓库信息和验证证据保存在本地。它是我从零实现的本地编程智能体。” |
| 10–22 秒 | 粘贴任务并发送；右侧计划出现 | “我给它一个带明确验收条件的真实缺陷：标签搜索失效，要求先补回归测试、最小修复，并完成定向和全量 pytest。” |
| 22–42 秒 | 加速展示 repo map、`TaskService.search`、已有测试；执行摘要只保留关键判断 | “模型只通过原生 function calling 请求本地工具。这里它先定位 service 和测试契约，计划与工具结果由本地 runtime 保存，不依赖服务端对话状态。” |
| 42–58 秒 | 新增回归测试后，定向 pytest 失败 | “新增的标签命中测试先失败，这说明问题被可复现地暴露。模型的文字声明不能算完成，DBAgent 会把这条失败保存为验证证据。” |
| 58–78 秒 | `apply_patch` 的变更摘要及变更文件 | “随后它用受限的多文件 patch 做最小修改。patch 会先校验全部上下文；任一 hunk 不匹配就整体拒绝，避免半应用状态。” |
| 78–98 秒 | 定向 pytest 通过，再展示完整 pytest 通过 | “修复后先跑针对性测试，再跑完整测试。只有当前的确定性检查通过，状态才会变为 VERIFIED。” |
| 98–110 秒 | 变更面板、`git diff`、完成计划、最终回答 | “这里能看到两个改动文件、增删行数、完成计划和 Git diff；整个执行 trace 还会以脱敏 JSONL 保留在 workspace 内。” |
| 110–120 秒 | 回到架构图或 README 的架构段落 | “核心模块包括本地 ContextManager、AgentLoop、ToolRegistry、路径 sandbox、PatchApplier 和 VerificationTracker。模型负责推理，本地 harness 负责执行、安全和验收。” |

讲稿正常语速约 105–115 秒。镜头 22–42 与 58–78 秒可加速，并在角落标注“中间过程
加速，命令与验证结果为实际运行输出”。不要播报 API 名称、token、完整本机用户名或目录。

## 观众应当看见的四个证据

1. **理解证据**：repo map / 关键文件定位，与结构化 plan 一致。
2. **缺陷证据**：新增的回归测试在修复前失败。
3. **修改证据**：patch 后变更列表与 Git diff 显示最小、可追溯的改动。
4. **完成证据**：定向和完整 pytest 都通过，verification 显示 `VERIFIED`。

不要用“模型很聪明”作为结论；上述四类可复现证据比主观评价更有说服力。

## 录制后的自检

- 总时长是否小于等于 120 秒，MP4 是否小于等于 200MB？
- 是否真实展示了失败、修复、通过三种状态，而不是只展示最终代码？
- 是否清楚说明了模型与本地 harness 的责任边界？
- 是否确认画面、trace、终端和字幕中没有 key、URL、token 或凭据文件内容？
- 是否将 `submission/README.txt` 的仓库地址占位符替换为最终公开仓库 URL，并确认其
  少于 1000 个中文字符？

## 面试时可展开的四个点

- **为何不用托管执行工具？** 所有文件、patch 与命令都在选定 workspace 本地执行，方便
  检查安全边界和复现执行证据。
- **为何要原子 patch？** 多文件变更先整体验证，避免模型因一个上下文不匹配而留下部分
  修改，失败能作为结构化 observation 继续处理。
- **为何要本地 context 管理？** 任务、plan、关键错误、代码片段和验证状态被预算化管理，
  不依赖 provider 的隐式 conversation state，也能恢复本地会话。
- **为何不能只相信最终回答？** 编程任务的完成定义是实际的 compiler/test/lint 证据；
  因此 `VERIFIED` 与模型的自然语言“完成”是两个不同状态。
